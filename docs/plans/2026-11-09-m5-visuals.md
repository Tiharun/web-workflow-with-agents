## 결정 (2026-11-09 사용자 확정)

1. **단계 자는 최종 워크플로우 가이드에만 붙인다.** builder는 동기 함수만 받는다(스펙 §3 시그니처 그대로). `stage-ruler`는 `siteConfig.ruler.guideId` 가이드에서만 그리고, 다른 가이드면 `null`이다. 지금의 비동기 교차 로딩은 없앤다. 단위 테스트가 설정에서 이 조합을 막는다.
2. **비주얼 실패를 경고 한 줄로 덮지 않는다.** 실패 종류마다 배포 전에 테스트가 막고, 실행 중에는 진짜 오류로 알린다.

   | 실패 | 배포 전(테스트가 실패) | 실행 중 |
   |---|---|---|
   | md 제목이 바뀌어 짝 없음 / builder가 `null` | DOM `every configured visual renders on its guide` | 스펙 §5대로 그 비주얼만 숨김. 예정된 상태라 오류 아님 |
   | 모르는 `type`, 다른 가이드의 `stage-ruler` | 단위 `every configured type is registered`·`stage-ruler only targets the ruler guide` | 모르는 type은 `reportError`로 알리고 건너뜀 |
   | builder가 예외를 던짐(코드 버그) | DOM `every configured visual renders on its guide` | `reportError(new Error('비주얼을 그리지 못함: …', { cause }))`로 알리고, 그 비주얼만 건너뛴 채 목차·진행 막대·모션은 계속 동작 |

   - `reportError()`는 오류를 콘솔과 전역 `error` 처리기에 '잡히지 않은 예외'처럼 보낸다([MDN](https://developer.mozilla.org/docs/Web/API/reportError)). 측정(Chromium 156): 전역 `error` 이벤트 1회, Playwright `pageerror`로 잡힘, 호출 뒤 코드는 계속 실행됨. 따라서 기존 e2e의 '콘솔 오류 0' 검사가 이런 오류를 그대로 실패로 잡는다.
   - `console.warn`·조용히 건너뛰기는 쓰지 않는다.

- 콘솔 오류 0(`pageerror`·`console.error`). 리뷰에서 나온 Minor도 같은 작업 안에서 테스트로 고친다(CLAUDE.md 규칙 7).

**Interfaces:**

- Produces:

`js/visuals.js`는 `md.js`·`guide.js`를 import하지 않는다(Node 단위 테스트에서 import되어야 한다. `ruler.js`→`icons.js`·`site-config.js`는 최상위에서 DOM을 쓰지 않음, 측정).

`placeVisuals` 규칙:
1. `list`에서 `guideId === guide.id`인 항목만, **등록 순서대로** 처리한다.
2. 제목은 `article.querySelector('#' + CSS.escape(headingId))`. 없으면 건너뛴다(스펙 §5, 오류 아님).
3. builder는 `visualTypes[type]`. 없으면 `reportError(new Error(\`알 수 없는 비주얼 종류: ${type}\`))` 뒤 건너뛴다. `try`로 호출하고, 던지면 `reportError(new Error(\`비주얼을 그리지 못함: ${type} → #${headingId}\`, { cause: err }))` 뒤 건너뛴다. `null`이면 건너뛴다(오류 아님). 이 두 문구는 개발자용 오류 메시지라 `siteConfig.ui`에 두지 않는다.
4. `<figure class="visual">`로 감싸 넣는다. 같은 제목에 이미 넣은 비주얼이 있으면 **그 뒤에**, 없으면 제목 바로 뒤에 넣는다(`Map<제목, 마지막으로 넣은 figure>`).
5. `'stage-ruler'` builder: `guide.id === siteConfig.ruler.guideId ? buildRuler(doc) : null`.

- [ ] **Step 2: DOM 테스트 작성** — `tests/dom/visuals.spec.mjs`

파일 안 도우미 `place(page, md, guideId, list)`: `blank.html`로 가서(이미 있으면 그대로) 한 번의 `page.evaluate` 안에서 `buildDoc(guideById(guideId), md)` → `#doc`(없으면 만듦)에 템플릿 복제 → 시험용 type을 `visualTypes`에 잠시 더하고 `placeVisuals(article, guide, doc, list)` → `finally`에서 시험용 type을 지운다. 시험용 type: `boom`(던짐), `a`·`b`(각각 `<div data-mark="a|b">` 반환). 반환값:
`{ visuals: [{ prev, inner }], textBefore, textAfter, errors }` — `prev`는 바로 앞 형제의 `id`(없으면 `'figure'`), `inner`는 figure 첫 자식의 `data-mark` 또는 `className`, `textBefore`/`textAfter`는 배치 전과 배치 후 `.visual`을 뺀 `#doc` 텍스트, `errors`는 배치하는 동안 전역 `error` 이벤트로 온 `event.error.message` 목록(`reportError`는 이벤트를 동기로 보낸다, 측정). 배치가 끝나면 리스너를 떼고, 테스트 페이지의 콘솔 오류로 남지 않게 그 이벤트에 `preventDefault()`를 부른다.

```js
// 고정 md: 제목 id는 siteConfig와 같은 GitHub 방식 slug가 된다.
const MD = `# 시험 가이드

## 1. 전체 루프 한눈에

루프 설명 문단.

## ${siteConfig.ruler.parentTitle}

### 0단계. 준비

### 4단계. 디자인 방향 고정 ★ 가장 중요

### 출시 게이트
`;
const v = siteConfig.visuals.find((x) => x.type === 'stage-ruler');
const at = (headingId, type, guideId = 'final') => ({ guideId, headingId, type });

test('the stage ruler sits right after its heading', async ({ page }) => {
  const r = await place(page, MD, 'final', [v]);
  expect(r.visuals).toEqual([{ prev: v.headingId, inner: 'ruler ruler--auto' }]);
  await expect(page.locator(`#doc .visual .ruler__stop`)).toHaveCount(3);
  expect(r.textAfter).toBe(r.textBefore);
  expect(r.errors).toEqual([]);
});

test('a missing heading hides only that visual without an error', async ({ page }) => {
  const r = await place(page, MD, 'final', [at('no-such-heading', 'stage-ruler'), v]);
  expect(r.visuals.map((x) => x.prev)).toEqual([v.headingId]);
  expect(r.textAfter).toBe(r.textBefore);
  expect(r.errors).toEqual([]);
});

test('an unknown type is reported', async ({ page }) => {
  const r = await place(page, MD, 'final', [at(v.headingId, 'no-such-type'), v]);
  expect(r.visuals.map((x) => x.inner)).toEqual(['ruler ruler--auto']);
  expect(r.errors).toEqual(['알 수 없는 비주얼 종류: no-such-type']);
});

test('a ruler on another guide is not drawn', async ({ page }) => {
  const r = await place(page, MD, 'steps', [at(v.headingId, 'stage-ruler', 'steps')]);
  expect(r.visuals).toEqual([]);
  expect(r.errors).toEqual([]);
});

test('a throwing builder is reported and skips only that visual', async ({ page }) => {
  const r = await place(page, MD, 'final', [at(v.headingId, 'boom'), at(v.headingId, 'a')]);
  expect(r.visuals.map((x) => x.inner)).toEqual(['a']);
  expect(r.errors).toEqual([`비주얼을 그리지 못함: boom → #${v.headingId}`]);
});

test('visuals on one heading keep their configured order', async ({ page }) => {
  const r = await place(page, MD, 'final', [at(v.headingId, 'a'), at(v.headingId, 'b')]);
  expect(r.visuals).toEqual([{ prev: v.headingId, inner: 'a' }, { prev: 'figure', inner: 'b' }]);
});

// 배포 전 관문: 실제 md로 등록된 비주얼을 하나씩 그려 본다. md 제목 변경·builder의 null·예외를 모두 여기서 잡는다.
test('every configured visual renders on its guide', async ({ page }) => {
  for (const x of siteConfig.visuals) {
    const g = guideById(x.guideId);
    const r = await place(page, readFileSync(g.file, 'utf8'), x.guideId, [x]);
    expect(r.visuals, `${x.guideId}#${x.headingId} (${x.type})`).toEqual([{ prev: x.headingId, inner: expect.any(String) }]);
    expect(r.errors, `${x.guideId}#${x.headingId} (${x.type})`).toEqual([]);
  }
});
```

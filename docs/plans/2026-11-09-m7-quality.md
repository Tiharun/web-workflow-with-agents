# M7 품질 패스 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 출시 게이트를 통과시킨다. 배포본 Lighthouse 성능·접근성 90 이상(모바일·데스크톱), 375~1920px와 200%·400% 확대에서 가로 넘침 없음, 키보드만으로 전부 조작, WCAG 2.2 AA 자동 검사 0건, 시각 기준 이미지 확정.

**Architecture:** 접근성·배치·키보드 기준을 먼저 테스트로 고정한 뒤(Task 2~4), 그 테스트를 안전망으로 성능을 고친다(Task 5~6). 성능의 근본 원인은 큰 본문을 한 번에 레이아웃하는 비용과 첫 화면이 GSAP 전체를 기다리는 모듈 사슬이다. 본문 블록에 `content-visibility: auto`를 주고, 등장 모션을 ScrollTrigger 대신 IntersectionObserver로 바꾸며, GSAP는 필요할 때 받는다. Lighthouse는 CLI로 재현 가능하게 돌린다(Task 1).

**Tech Stack:** 바닐라 ES 모듈, GSAP 3.15.0(core만), `@playwright/test` 1.64.1, `@axe-core/playwright` 4.14.0(새 devDependency), Lighthouse CLI 13.5.0(`npx`, 의존성 아님), Node 22.21, Python `tests/serve.py`.

**Spec:** [docs/specs/2026-11-08-guide-site-design.md](../specs/2026-11-08-guide-site-design.md) §2, §6, §8 M7. 기준: [brief](../brief.md) '성공 기준', [DESIGN.md](../../DESIGN.md) '모션'.

**브랜치:** `main`(d5e322d, M6 병합)에서 `m7-quality`.

## 결정 (사용자 검토 필요 항목은 ★)

1. ★ **본문 블록 `content-visibility: auto`.** 측정(아래)에서 final 본문 레이아웃이 약 1,200ms → 20ms로 준다. 화면 밖 블록은 낭독기 트리·Tab 순서·Ctrl+F에 그대로 남는다([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/content-visibility)). 대가: Safari 18 미만·Firefox 125 미만은 효과 없음(무시될 뿐 깨지지 않음), Safari의 Ctrl+F가 화면 밖 글을 못 찾는다는 보고가 있다([WebKit 283846](https://bugs.webkit.org/show_bug.cgi?id=283846), 수정 여부 확인되지 않음). 대안은 모바일 성능 기준을 낮추는 것뿐이다.
2. **등장 모션 = IntersectionObserver + GSAP core.** `content-visibility`를 켜면 블록 높이가 추정값이 되어 ScrollTrigger의 미리 잰 위치가 틀린다. IO는 실제 교차만 보므로 영향이 없다. ScrollTrigger·Observer(gzip 약 40KB)를 뺀다. 동작 규칙(DESIGN.md: 28px, 0.9초, `expo.out`, 간격 0.08초·묶음 0.24초 상한, 한 번만, 건너뛴 블록은 즉시)은 그대로다.
3. **GSAP 지연 로드.** `motion.js`는 GSAP를 정적 import하지 않고 처음 필요할 때 `import()`한다. 동작 줄이기면 아예 받지 않는다. 받기 실패면 모션 없이 글만 보인다. 홈 단계 자는 GSAP를 받은 뒤 그린다(스켈레톤이 그동안 자리를 지킨다) — 첫 방문에도 그리기 연출이 유지된다.
4. **Lighthouse = CLI.** chrome-devtools-mcp의 `lighthouse_audit`은 성능을 빼고 잰다(도구 설명, 측정). 그래서 `npx lighthouse@13.5.0`(13.6.0은 2026-10-27 출시로 2주 미만)을 `tools/lighthouse.mjs`가 돌린다. 화면마다 3회 중앙값으로 판정한다. 배포 전 확인용으로 GitHub Pages처럼 gzip을 주는 로컬 서버 옵션을 둔다(로컬 http.server는 압축이 없어 점수가 55 안팎으로 왜곡됨, 측정).
5. **WCAG 자동 검사 = axe-core.** 태그 `wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa`(대비 1.4.3, 누르는 영역 2.5.8 포함). 화면 9종 × 라이트·다크 × 375·1280.
6. **확대 = 200%(1.4.4)와 400%(1.4.10 Reflow).** 브라우저 확대는 CSS 뷰포트가 줄어드는 것과 같으므로 1280×900 창을 `viewport 640×450, deviceScaleFactor 2`(200%)와 `320×225, 4`(400%)로 흉내 낸다. 400%는 brief의 'WCAG 2.2 AA'에 1.4.10이 포함되어 넣는다([W3C Understanding Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow): 표의 칸 하나하나도 대상). 글자만 확대(Firefox)는 다루지 않는다.
7. **누르는 영역 예외.** 문장 안 링크·용어 버튼(`.term`, 23px)은 2.5.8 'Inline' 예외다(이미 `css/site.css:10`에 기록). 읽기 전용 체크박스는 `disabled`라 대상이 아니다.

# 웹사이트 제작 순서 (Claude와 함께 만들기)

> 이 문서는 "결정은 앞에서 글로 고정하고, 코드는 얇게 전체를 먼저 관통시킨 뒤 기능별로 살을 붙인다"는 원칙으로 짜여 있습니다.
> 각 단계는 **할 일 → 결과물 → Claude에게 보낼 요청 예시 → 다음 단계로 넘어가기 전 확인**으로 구성됩니다.
> 핵심 원칙 3가지만 기억하세요.
>
> 1. **코드보다 결정이 먼저.** 1~5단계에서 결정을 문서로 고정하지 않으면 모델이 매 세션 다르게 해석합니다.
> 2. **디자인은 "나중에 꾸미기"가 없다.** 4단계에서 최종 품질로 결정하고, 6단계 골격부터 그 품질로 만듭니다.
> 3. **전체를 얇게 먼저, 기능은 하나씩.** 빈 페이지라도 전 페이지가 실제 URL에서 열리는 상태를 먼저 만듭니다.

"권장 노력 수준"은 Claude 모델의 추론 노력(effort) 설정 기준이며 강제 규칙이 아니라 권유입니다. 결정 단계(1~5)에 힘을 쓰고, 구현 단계는 중간이면 충분한 경우가 많습니다.

## 1단계. 범위 정의 (코드 없음, 대화만)

### 할 일
- 이 사이트가 **왜** 존재하는지 한 문장으로 적기
- **누가** 쓰는지 (대상 사용자 1~2유형)
- **핵심 기능 3~5개**만 고르기 (그 이상은 2차로 미루기)
- **안 만들 것** 명시하기 (로그인 없음, 결제 없음, 모바일 앱 없음 등)
- 성공 기준 1~2개 (예: "친구 10명이 하루 한 번 들어온다")

### 결과물
`docs/01-범위.md` 또는 설계 문서 안의 "범위" 섹션

### Claude에게 보낼 요청 예시
```
웹사이트를 만들려고 해. 아직 코드는 쓰지 말고 범위만 같이 정리해 줘.
- 목적: (한 문장)
- 대상: (누가 쓰는지)
- 떠오르는 기능: (생각나는 대로 나열)
이 중에서 1차 출시에 꼭 필요한 핵심 기능 3~5개를 골라 주고,
나머지는 "2차 이후"로 분류해 줘. 모호한 부분이 있으면 질문해 줘.
```

### 넘어가기 전 확인
- [ ] 핵심 기능이 5개 이하인가?
- [ ] "안 만들 것" 목록이 있는가?
- [ ] 기능 설명을 읽고 다른 사람이 똑같이 이해할 수 있는가?

> ⚠️ 초보자가 가장 많이 하는 실수: 기능을 10개 이상 넣고 시작하는 것. 작게 끝내고 늘리는 게 훨씬 빠릅니다.

## 2단계. 구조 설계

### 할 일
- **페이지 목록(사이트맵)**: 어떤 페이지가 있고, 어디서 어디로 이동하는지
- **각 페이지의 역할** 한 줄씩
- **데이터 모델**: 저장할 정보가 있다면 어떤 항목이 있는지 (예: 게시글 = 제목, 내용, 작성일)
- **상태 흐름**: 사용자가 입력하면 무엇이 바뀌는지

### 결과물
`docs/02-구조.md` — 사이트맵 + 데이터 모델 표

### Claude에게 보낼 요청 예시
```
1단계에서 정한 범위를 바탕으로 사이트 구조를 설계해 줘. 아직 코드는 쓰지 마.
1) 페이지 목록과 각 페이지의 역할 한 줄
2) 페이지 간 이동 흐름 (텍스트 다이어그램이면 충분)
3) 저장해야 하는 데이터가 있다면 항목별 필드 목록
빠진 페이지나 애매한 흐름이 있으면 질문해 줘.
```

### 넘어가기 전 확인
- [ ] 모든 핵심 기능이 어떤 페이지에서 일어나는지 정해졌는가?
- [ ] 데이터가 있다면 필드 이름과 타입까지 정해졌는가?
- [ ] 404 페이지, 빈 상태(데이터 없을 때) 화면도 목록에 있는가?

### 할 일

- **패키지 매니저, 포매터, 린터** 결정

### 결과물

### Claude에게 보낼 요청 예시

## 4단계. 디자인 방향 고정 ★ 가장 중요한 단계

### 이 단계가 중요한 이유
디자인 퀄리티는 **여기서만** 결정됩니다. "일단 뼈대로 만들고 나중에 꾸미자"는 Claude와 작업할 때 거의 실패합니다.
- 모델은 "나중"을 스스로 기억하지 않습니다. 폴리시 단계가 명시돼 있지 않으면 그 단계는 오지 않습니다.
- "목업", "시안", "뼈대", "와이어프레임" 같은 단어는 저충실도 신호로 읽혀 회색 박스가 나옵니다.
- 첫 결과를 승인하면 그 수준이 **기준선**이 됩니다. 기능이 다 붙은 뒤 디자인을 바꾸면 모든 컴포넌트를 손봐야 해서 모델이 "최소 변경"으로 끝내려 합니다.

### 할 일
1. **참고 사이트 2~3개** 고르기 (링크 + "이 사이트의 어떤 점이 좋은지" 한 줄)
2. **분위기를 단어로** 정하기 (예: 차분한, 또렷한, 장난스러운, 미니멀, 따뜻한)
3. **디자인 토큰** 정하기 — Claude에게 제안받고 승인
   - 색: 배경, 본문 글자, 강조색 1~2개, 경계선, 성공/오류
   - 타이포: 제목 폰트, 본문 폰트, 크기 단계(예: 12/14/16/20/24/32)
   - 간격: 4px 배수 체계 (4/8/12/16/24/32/48)
   - 라운드, 그림자, 다크 모드 여부
4. **대표 페이지 1개를 최종 출시 수준으로** 구현해서 승인
   - 내용은 가짜여도 되지만 **생김새는 완성본**이어야 함

### 결과물
- `docs/04-디자인.md` — 토큰 표 + 참고 사이트 + 분위기 단어
- 실제로 열리는 대표 페이지 1개 (브라우저에서 확인 가능)

### Claude에게 보낼 요청 예시
```
디자인 방향을 정하려고 해. "시안"이나 "목업"이 아니라
**최종 출시 수준의 비주얼**로 대표 페이지 1개를 만들어 줘.

참고 사이트:
- (링크) — 여백이 넓고 글자가 또렷한 점이 좋음
- (링크) — 카드 레이아웃과 색 대비가 좋음
원하는 분위기: 차분하고 깔끔한, 과하지 않은

먼저 디자인 토큰(색, 타이포, 간격, 라운드, 그림자)을 표로 제안해 줘.
내가 승인하면 그 토큰으로 (페이지 이름) 페이지를 구현해 줘.

완료 기준:
- 프레임워크 기본 폰트/기본 색상이 그대로 남아 있으면 미완료
- 회색 박스나 "여기에 이미지" 같은 자리표시자가 있으면 미완료
- 모바일(375px)과 데스크톱(1280px) 둘 다 깨지지 않아야 함
```

### 결과를 확인하는 방법 (초보자용)
- 브라우저에서 직접 열어 보고 스크린샷을 찍어 둡니다.
- 아래 중 하나라도 해당하면 **승인하지 말고 반려**합니다.
  - 기본 시스템 폰트(Arial, Times 등)가 그대로 보인다
  - 색이 파란 링크 + 검정 글자 + 흰 배경뿐이다
  - 회색 사각형, "Lorem ipsum", "이미지 자리"가 보인다
  - 참고 사이트와 비교했을 때 "덜 만들어진" 느낌이 든다
- 반려할 때는 이렇게 보냅니다:
  ```
  지금 결과는 와이어프레임 수준이야. 이 수준으로 승인하지 않을 거야.
  (참고 사이트) 수준의 완성도로 다시 만들어 줘.
  특히 (폰트 / 색 대비 / 여백 / 카드 그림자)가 부족해.
  ```

### 넘어가기 전 확인
- [ ] 디자인 토큰이 문서에 표로 적혀 있는가?
- [ ] 대표 페이지가 "이대로 출시해도 된다" 수준인가?
- [ ] 모바일과 데스크톱 스크린샷을 둘 다 봤는가?
- [ ] "이 결과가 앞으로의 기준선이 된다"고 생각하고 승인했는가?

## 5단계. 설계 문서 + 마일스톤 작성

### 할 일
- 1~4단계 결정을 **한 곳에 모은 설계 문서** 만들기
- 프로젝트 루트에 **CLAUDE.md** 만들기 (매 세션 Claude가 자동으로 읽는 파일)
- 작업을 **마일스톤**으로 쪼개고, 각 마일스톤에 **완료 판정 기준** 적기

### CLAUDE.md에 반드시 들어갈 것
```markdown
# 프로젝트명

## 목적 (한 문장)

## 기술 스택
- 프레임워크 / 호스팅 / 데이터 저장 방식
- 실행: `npm run dev`, 빌드: `npm run build`

## 디자인 토큰 (변경 금지)
- 배경 #…, 본문 #…, 강조 #…
- 제목 폰트 …, 본문 폰트 …
- 간격 4px 배수, 라운드 8px, 그림자 …
- 기본 폰트/기본 색 사용 금지

## 코딩 규칙
- 공용 컴포넌트는 components/ 에만 둔다
- 새 페이지는 기존 레이아웃을 반드시 사용한다
- 작업 후 반드시 브라우저로 확인하고 스크린샷을 보여 준다

## 현재 마일스톤
- M1: … (완료 기준: …)
```

### 마일스톤 쪼개는 요령
- 한 마일스톤 = **한 세션에서 끝낼 수 있는 크기** (대략 페이지 1개 또는 기능 1개)
- 완료 기준은 **눈으로 확인 가능한 문장**으로:
  - ✗ "게시판 구현" → ○ "목록 페이지에서 글 3개가 보이고, 클릭하면 상세 페이지로 이동한다"
- 디자인 폴리시가 필요하면 **별도 마일스톤으로 명시** (명시하지 않으면 오지 않음)

### Claude에게 보낼 요청 예시
```
1~4단계 문서를 보고 다음을 만들어 줘.
1) CLAUDE.md — 위 템플릿 구조로, 디자인 토큰은 "변경 금지"로 표시
2) docs/설계.md — 범위·구조·스택·디자인을 한 문서로 통합
3) docs/마일스톤.md — 각 마일스톤에 "눈으로 확인 가능한 완료 기준"을 2~4개씩
마일스톤 하나는 한 세션에 끝날 크기로 쪼개 줘.
```

### 넘어가기 전 확인
- [ ] CLAUDE.md에 디자인 토큰과 코딩 규칙이 있는가?
- [ ] 모든 마일스톤에 완료 기준이 있는가?
- [ ] 완료 기준이 "눈으로 확인 가능한 문장"인가?

## 6단계. 골격 구현 → 즉시 배포

### 할 일
- 프로젝트 초기화 + Git 저장소 생성
- **라우팅**: 2단계 사이트맵의 모든 페이지를 빈 상태로 생성
- **공통 레이아웃**: 헤더, 내비게이션, 푸터 — **4단계 토큰으로 최종 품질**
- **공용 컴포넌트**: 버튼, 카드, 입력창 등 — 최종 품질
- **배포 파이프라인**: 푸시하면 자동 배포되게 설정
- 실제 URL에서 **전 페이지가 열리는지** 확인

### 디자인 관련 주의
골격이라고 해서 생김새를 대충 만들지 않습니다. **내용만 비어 있고 생김새는 완성본**입니다. 여기서 만든 공용 컴포넌트를 7단계에서 조립하기 때문에, 여기 품질이 곧 사이트 전체 품질이 됩니다.

### Claude에게 보낼 요청 예시
```
CLAUDE.md와 docs/를 읽고 골격을 만들어 줘.
- 사이트맵의 모든 페이지를 생성 (내용은 제목만)
- 공통 레이아웃(헤더/내비/푸터)과 공용 컴포넌트(버튼/카드/입력창)는
  CLAUDE.md의 디자인 토큰으로 **최종 품질**로 구현
- 배포 설정까지 완료
완료 기준: 배포된 URL에서 모든 페이지가 열리고,
헤더/푸터가 4단계 대표 페이지와 동일한 품질이어야 함.
끝나면 각 페이지 스크린샷을 보여 줘.
```

### 넘어가기 전 확인
- [ ] 배포된 실제 URL이 있는가?
- [ ] 모든 페이지가 404 없이 열리는가?
- [ ] 헤더/푸터/버튼이 4단계 대표 페이지와 같은 품질인가?
- [ ] Git에 커밋되어 있는가?

## 7단계. 마일스톤별 기능 구현

### 할 일 (마일스톤마다 반복)
1. **새 세션 시작** (가능하면) — 컨텍스트를 깨끗하게 유지
2. "CLAUDE.md와 docs/마일스톤.md를 읽고 M○를 구현해 줘"
3. 구현 완료 후 **브라우저로 실제 확인** (스크린샷 또는 자동화 도구)
4. 완료 기준을 하나씩 체크
5. 통과하면 **커밋**, 실패하면 반려 후 수정
6. 마일스톤 문서에 완료 표시

### Claude에게 보낼 요청 예시
```
CLAUDE.md와 docs/마일스톤.md를 읽고 M2를 구현해 줘.
- 6단계에서 만든 공용 컴포넌트를 재사용하고, 새 스타일을 임의로 만들지 마
- 완료 기준을 하나씩 확인한 결과를 스크린샷과 함께 보여 줘
- 통과하면 커밋 메시지를 제안해 줘
```

### 반려할 때
```
완료 기준 2번("…")이 충족되지 않았어. (스크린샷 설명)
이 부분만 수정해 줘. 다른 부분은 건드리지 마.
```

### 넘어가기 전 확인 (마일스톤마다)
- [ ] 완료 기준 전부 통과했는가?
- [ ] 새로 만든 화면이 기존 화면과 같은 디자인 품질인가?
- [ ] 커밋했는가?

> 한 번에 여러 마일스톤을 시키지 마세요. "M2~M5 전부 해 줘"는 중간에 품질이 떨어지고 통합할 때 깨지는 가장 흔한 패턴입니다.

## 8단계. 실제 콘텐츠·카피·메타 채우기

### 할 일
- 더미 텍스트 → 실제 문구로 교체
- 이미지, 아이콘, 로고 넣기
- **SEO 메타**: 페이지별 `<title>`, `description`
- **OG 태그**: 링크 공유 시 보이는 제목·설명·이미지
- favicon
- 404 페이지 문구, 빈 상태 문구

### Claude에게 보낼 요청 예시
```
실제 콘텐츠를 채우는 단계야.
1) 모든 더미 텍스트 위치를 목록으로 뽑아 줘 → 내가 문구를 줄게
2) 페이지별 title/description, OG 태그, favicon 설정
3) 404와 빈 상태 화면 문구를 사이트 톤에 맞게 제안해 줘
```

### 넘어가기 전 확인

- [ ] 브라우저 탭에 favicon이 보이는가?

## 9단계. 품질 패스

### 할 일
- **반응형**: 375px(모바일), 768px(태블릿), 1280px(데스크톱) 확인
- **접근성**: 키보드만으로 이동 가능, 이미지 alt, 색 대비
- **성능**: Lighthouse 점수 확인 (모바일 기준 90 이상 목표)
- **에러 상태**: 네트워크 실패, 데이터 없음, 잘못된 URL
- **디테일 폴리시**: 호버/포커스 효과, 간격 미세조정, 로딩 표시

### Claude에게 보낼 요청 예시
```
품질 패스를 진행해 줘. 디자인 토큰과 레이아웃은 바꾸지 말고 디테일만 다듬어.
1) 375/768/1280px에서 전 페이지 스크린샷 → 깨지는 곳 수정
2) 키보드 탐색과 alt 텍스트, 색 대비 점검
3) Lighthouse 실행 → 점수와 개선 항목 보고
4) 빈 상태·에러 상태·로딩 상태가 없는 화면 목록 → 추가
```

### 넘어가기 전 확인
- [ ] 3가지 화면 폭에서 깨지는 곳이 없는가?
- [ ] Tab 키만으로 모든 버튼/링크에 갈 수 있는가?
- [ ] Lighthouse 성능·접근성 점수를 확인했는가?
